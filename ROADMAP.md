### Item (b) — fixed schema (DONE)
**Real gateway finding, checked live, not assumed** (per the project's Honesty rule). `config/models.json` declares `"structured_output": true` for claude-haiku-4-5/claude-sonnet-5-5/gemini-3.8-flash, but nothing in the code ever reads that flag — `app.providers.generation.openai_compat.generate_structured` has always worked by parsing the model's raw text as JSON (with one repair call if it isn't parseable), never by asking the gateway to enforce a schema. Tested live against the real gateway (apimaster.ai, claude-haiku-4-5, 2026-10-16), three ways, same prompt:
- `response_format: {"type": "json_schema", ...}` → **HTTP 200, but no effect**: the response is byte-identical to no `response_format` at all, including stray markdown fences and a shape that doesn't match the declared schema (the model freely returned `{"fact": "..."}` instead of the requested `{"facts": [...]}`). apimaster proxies this model to the real Anthropic API (`"usage_source": "anthropic"` in every response's `usage` block) — Anthropic's native API has no equivalent to OpenAI's `response_format`, so the gateway silently drops the parameter when translating.
- `response_format: {"type": "json_object"}` → same: HTTP 200, identical output, no enforcement.
- Forced tool-calling (`tools: [...]`, `tool_choice` naming the function) → **genuinely enforced**: the reply came back as a `tool_calls` entry whose `arguments` exactly matched the declared JSON schema, no markdown fences, correct field names and types. This is the one mechanism that actually constrains output on this gateway for an Anthropic-backed model (translates cleanly to Claude's native tool-use).

**Scope decision**: switching the three research-pipeline stages to forced-tool-calling as their generation transport is real, available, and would be the strongest fix — but it means changing `app.providers.generation`, which every one of the 18 roles shares, for a benefit scoped to 3 of them. Deferred as a separate, explicitly-flagged future change (tracked here, not silently dropped); what was built instead satisfies the spec's own fallback instruction exactly ("else validate + one repair call. Invalid after repair = recorded failure, never a silent skip") using the existing, already-safe text-based transport.

**Built**: one pydantic model per stage, `app/agents/research_schemas.py` — `FactExtractorOutput`, `TimelineBuilderOutput`, `ContradictionAnalyzerOutput` (field shapes taken directly from each stage's own `output_schema` dict already in research.py). A new `_validate_or_repair()` helper (app/agents/research.py) is used at all three call sites (`_extract_batch`, `_build_timeline`, `_analyze_contradictions`): validates the reply against its schema; on failure, one repair call telling the model exactly which fields failed and why; still invalid after that raises the same `GenerationError` the pre-existing JSON-parse-failure path already uses (so it is a real recorded `AgentRun` failure with the summed real billed tokens of both calls — no spend lost from the ledger, no silent skip). The literal `run_agent("research.extract_facts", ...)`-style call stays inline at each of the three call sites rather than moving into the shared helper, because `tests/test_architecture.py::test_agent_names_in_code_are_defined_and_every_agent_is_used` statically greps the source for exactly that literal pattern to confirm every `config/agents.json` entry is actually used — a first version that passed the agent name through the helper as a variable broke that check (caught by the full suite, fixed by only sharing the repair-call logic, not the first call). `model_dump(exclude_unset=True)` is used (not the plain dump) so a field the model never set stays ABSENT rather than becoming an explicit `null` — this matters because `_resolve_fact_span`'s backward-compatibility path (Part 2(e) item 4) distinguishes "no `supporting_span` key at all" from "`supporting_span: null`"; a first attempt at this used the plain dump and broke that exact path (caught before committing, by reasoning through the diff, not by the test suite — the regression was confirmed to actually reproduce, then fixed, then re-verified green). The module docstring in `research_schemas.py` also had to be reworded once: it originally named the real model/gateway from the live probe above, which tripped `test_no_hardcoded_model_ids_anywhere_in_app`/`test_no_hardcoded_provider_names_in_agents` (no model id or provider name may appear anywhere under `app/`, including comments) — the concrete names stay here in ROADMAP.md only.

**Scoping of what's validated**: structural correctness only (required fields present, right types, well-formed nested objects like `supporting_span`) — not the open-ended categorical fields (`narrative_value`, `evidence_strength`, `quote_status`, free-text `category`) the prompts describe as enums but the rest of the codebase already treats as free strings (`_store_facts` defaults an unrecognized `category` to `"general"` rather than rejecting it). Enforcing those as strict enums would turn harmless model drift on a non-critical field into a paid repair call for no correctness gain; documented in `research_schemas.py`'s own module docstring.

Tests: `tests/test_evidence_depth.py::test_schema_invalid_fact_extractor_output_is_repaired_once` (a fact missing `claim` with non-numeric `confidence` triggers exactly one repair call; a valid repair reply is stored normally) and `::test_schema_invalid_fact_extractor_output_is_a_recorded_failure_not_a_silent_skip` (still invalid after repair raises `GenerationError`, stores zero facts, and leaves a `status="failed"` `AgentRun` row with the validation error — not a silent skip). **Real gaps fixed** (app/agents/story.py):

Fixed: `_strongest_facts` now returns `(kept, dropped)`, and `build_evidence_pack`'s result carries a new `pack["evidence_diet"]` key: `{cap, kept, dropped: [{fact_id, reason}]}`.
