# 9J Part 2 — closing per-type evidence gaps

Starting state (before this part): 1/24 types SOUND (`research_result`); 23
UNPROVEN, each listing which perturbation(s) failed to reach every direct
consumer with a strong (code-cited) explanation. The full per-type table for
all 24 types is `docs/architecture/soundness-matrix.md` (auto-generated by
`tests/generate_soundness_status.py` from the committed Phase 4/5 snapshot-diff
records — this doc records what changed and why, not a duplicate table).

## A structural gap, not three isolated ones

`agent_model_routing`'s "missing strong direct-consumer effect: beats:shared,
host_plan:shared, master_story:shared, naming:shared" line appeared in the
UNPROVEN reason for every single one of the other 22 types — it, and the same
four-key pattern under `typed_config_documentary`, were the single highest-
leverage blockers. Investigating why led to a structural finding:
**no config-sourced perturbation ever got `no_effect_edges()` computed.**

`tests/run_soundness_phase5.py` derives `source_type` from
`evidence["source_changed"][0]`. For a real-artifact perturbation that is e.g.
`"master_story:shared"` → `source_type = "master_story"`. For a config-sourced
one, `prepare_phase5()` (`tests/soundness_replay.py:482`, previously line
~mid-400s) records it as `f"config:{source}"` — so `source_type` is always the
literal string `"config"`, which never matches the function's allow-list. This
affects all 15 config-sourced perturbations (`agent_model_routing`, all
`typed_config_*`, `channel_identity_logo`, `logo_bytes`, `intro_design`,
`language_profile`, `pronunciation_voice`, `music_history_library`), not just
the two investigated here.

### Fix

- `tests/soundness_replay.py`: `no_effect_edges()` gained a `config_source`
  keyword. When set, direct consumers are computed from
  `ARTIFACT_CONFIG_INPUTS`/`CONFIG_SECTIONS` (the same mapping
  `tests/generate_soundness_status.py` already uses for the predicted-set
  column), at the single representative language `"en"` for per-language
  types — matching that generator's own `_scoped_key()` convention. The
  previously-inline `reasons` dict is now `NO_EFFECT_REASONS`, keyed by
  perturbation name for config sources (reuses the same tuple shape, no
  collision with real-root keys).
- `tests/run_soundness_phase5.py`: when `source_type == "config"`, calls
  `no_effect_edges(None, None, actual, config_source=source)` instead of
  skipping the call entirely.
- `CONFIG_SECTIONS` was duplicated identically in `prepare_phase5()` and (as a
  separate copy) in `tests/generate_soundness_status.py`; the first copy is now
  a single module-level constant in `soundness_replay.py` that both
  `prepare_phase5()` and `no_effect_edges()` use. `generate_soundness_status.py`
  keeps its own copy (a different module, the matrix generator) — not touched,
  since changing it isn't needed for this fix and it is independently correct.

## Edges closed, each re-run through the real pipeline (not hand-derived)

Every fix below was applied as a committed, cited reason, then
`SOUNDNESS_ONLY=<name> python tests/run_soundness_phase5.py` was re-run for
real and its output record merged into `tests/golden/soundness_phase5_results.json`
(verified by diff: only `no_effect_edges`/timing/evidence-path fields changed;
`actual`/`predicted`/`hidden`/`over_invalidation` were byte-identical to the
pre-fix record, confirming the fix only added explanation, not new behavior).

**`agent_model_routing`** (routing['chapter_writer'] only) → now strong.
`beats`/`host_plan`/`master_story`/`naming` are produced by the
`visual_planner` / `host_director`,`host_writer` / `master_story_director`,
`master_writer` / `case_naming_agent` roles respectively (`config/agents.json`)
— none of them `chapter_writer` — and the mocked request payload embeds
`ai_config.model_for(role)` (`tests/mock_payload.py:126,133`), which is
per-role and therefore unaffected by changing only `chapter_writer`'s routing.

**`typed_config_documentary`** (`ai_config.documentary.pilot_seconds += 1`) →
now strong. `app/documentary/jobs.py:238` reads it as
`job.pilot_seconds or ai_config.documentary.pilot_seconds`; this fixture's job
is created with an explicit `pilot_seconds=80.0`
(`tests/test_visual_production.py:1406-1407`), which always wins the `or`, so
the config field is never read in this run at all — not a threshold-sensitivity
issue, a complete shadow. (Docs/architecture/dead-config.md previously flagged
this field as "read but zero-effect, UNPROVEN, not dead-config" — this closes
that specific open question for this fixture: it isn't that the effect is too
subtle, it's that the field is unreachable here. It should still be considered
read-but-unexercised for a pilot-less/API-triggered fixture.)

**`master_story`** (appends to `story_text`/`narrative_structure` only) → now
strong, for its two previously-weak edges:
- `naming:shared`: `app/naming/context.py:54-103` (`build_context`) reads
  `case.canonical_title`, `case.summary` and the blueprint; never
  `StoryVersion.story_text`/`narrative_structure`.
- `chapter_plan:shared`: `app/agents/chapters.py:29` does read
  `master.narrative_structure`, but `_payload()` (chapters.py:45-67) only
  embeds `ctx['acts']`/`ctx['events']`, built by `acts_of()`/`told_events()`
  (`app/documentary/chapters.py:69-89`), which read `structure['acts']` (plan
  metadata: id/title/purpose), never `structure['sections']` (the prose text
  this perturbation actually changes).

## Investigated but not yet closed (honest list)

**`one_beat`** (`blueprint_json["beats"][0]["summary"]` edited) — the single
most pervasive remaining blocker, listed for `beats`, `host_plan`,
`chapter_plan`-adjacent, `audio_blocks`, `timeline_cards`, `visual_needs`.
Two of its five missing edges were traced to a clean, citable reason during
this investigation (not yet committed, since the other three need the same
rigor before committing the group):
- `chapter_plan:shared`: beat B01 (confirmed by direct DB inspection of a real
  run) has `purpose: "hook"`; `acts_of()` (`app/documentary/chapters.py:87-88`)
  only folds a beat's `summary` into `reveals` when
  `purpose in ai_config.attention.firewall_purposes`
  (`app/core/ai_config.py:1424-1425`, default
  `["reveal","contradiction","evidence","false_lead","chapter_end"]` — "hook"
  is not in it).
- `timeline_cards:en`: `told_events()` (`app/documentary/chapters.py:99-108`)
  only reads `EVENT_IDS = ("reveals","relies_on","viewer_knows")`
  (chapters.py:49), never `summary`.

Still open for `one_beat`: `audio_blocks:shared`, `host_plan:shared`,
`visual_needs:shared`. Leads found, not yet verified to the same standard:
- `visual_needs`: produced via the `visual_planner` role
  (`app/documentary/jobs.py:361`), whose mocked response in this fixture is a
  hardcoded, input-independent dict (unlike most other roles, it does not
  embed `_mock_request_sha256`) — plausibly insensitive to *any* upstream
  change in this fixture, not just this one, but not yet confirmed by a
  second, different perturbation.
- `audio_blocks`: `app/documentary/audio_director.py:151-169`
  (`_director_input`) *does* embed `b.get("summary")` in the audio-director
  request, so the request fingerprint should change; `app/agents/audio_plan.py`
  then runs it through `validate_audio_plan(raw, blueprint)` before persisting
  — the suspected cause is that validation only keeps the plan's own declared
  schema and drops the injected `_mock_request_sha256` field, but this was not
  traced into `validate_audio_plan`'s source before this part ended.
- `host_plan`: `director_input()` (`app/documentary/host.py:214-230`) also
  embeds `b.get("summary")` for every beat; `host_*` roles are dispatched to a
  separate `HostGen` fake (`tests/test_host.py`) rather than the generic
  fingerprint-echoing branches other roles use, and whether `HostGen`'s
  returned structure is sensitive to beat-level text differences was not
  traced before this part ended.
