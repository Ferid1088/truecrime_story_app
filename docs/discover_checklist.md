## Resolution-status criterion (owner-added, after the original pasted task)

The owner replaced the plain "Include unsolved cases" checkbox with a 3-way choice, after reviewing the subagent-verification above:

- `TopicDiscoveryRequest.resolution_filter: Literal["solved_only", "unsolved_only", "both"] = "solved_only"` (`app/schemas.py`) — same default behaviour as the old unchecked checkbox.
- Threaded through every layer that used to carry `include_unsolved: bool`: `app/services/research_jobs.py` (`_discovery_input`, `start_discovery_job`, `_ingest_discovery`), `app/providers/base.py`, `app/research_engine/provider.py`, `app/research_engine/orchestrator.py`, `app/lifecycle/selection.py` (`prepare_candidates`, `ingest_candidates`, `_prepare_sync`, new `_passes_resolution_prefilter` helper).

- Existing call sites that passed the old `include_unsolved=True/False` keyword (`tests/test_case_lifecycle.py`, `tests/test_discovery_quality.py`) were updated to the equivalent `resolution_filter="solved_only"/"both"` — a mechanical, faithful translation, not a behaviour change.
- Generated Search name (D2, not yet built) and the Searches-list chip for this axis are deferred to D2, which stores the full criteria already (nothing here blocks it).

## Unproven / open questions

- **Model-call cost for discovery is still not captured.** Job 38's `model_cost_usd` is `0.0` even though candidate extraction and status verification genuinely ran (1 candidate returned, `selection_stats.verified: 5`, `status_searches: 10`). `accumulate_telemetry` (`app/research_engine/planner.py:138`) only adds cost when the generation provider's `GenerationResult.cost_usd` is truthy, and that in turn only comes from the gateway's self-reported `usage["cost"]` (`app/providers/generation/openai_compat.py:261`) — there is no fallback computed from token counts via `config/parameters/pricing.json`, unlike what `ProviderCall.cost_source`'s `"computed_from_tokens"` value implies exists elsewhere in the system. Net effect: **discovery's reported cost today is a floor (search cost only), not the true total** — real spend is understated by whatever the LLM calls actually cost. Flagging this rather than silently fixing it: the fallback-from-tokens path needs to be located or built deliberately, and may affect more than discovery. Not fixed in this pass; the D5/D7 "real cost" reporting I build will carry this caveat forward until it is.
